### 1.3 구조적 원인
1. **포맷 정의가 다섯 군데에 흩어져 있다**: format, formatType, stages[], *Config, scoring 사본. 경기의 의미를 stageId 문자열 매칭("_3rd", "_class_", "5to8")으로 추론한다(rankings-compute.ts:79, 131; RankingTab.tsx:24).
2. **같은 로직이 4~6벌 중복되고 서로 다르게 바뀌어 왔다**:
   - 리그 생성: bracket.ts, tournament.ts, BracketTab, schedule.ts, setup-full, simulation
   - 순위: 약 7곳
   - 스케줄러: 2곳
3. **클라이언트 경로가 더 약하다.** 더 강한 서버 엔진은 챗봇 도구로만 도달할 수 있다(chatbot-tools.ts:332, 574, 730). 클라이언트 src에는 `httpsCallable`이 없다.
4. **match.round의 의미가 경로마다 다르다.** 실행 카운터, 대진 라운드, 티어 내 순번이 섞여 있다(BracketTab.tsx:157; generate-finals.ts:140; setup-full.ts:251).

## 2. 목표 아키텍처: Universal Format Engine

### 2.1 원칙
- **Format-as-data**: 대회 형식은 코드가 아니라 `definition` 데이터로 표현한다. 프리셋은 이 데이터를 채우는 템플릿일 뿐이다.
- **Single source of truth**: 순수 TypeScript 엔진 패키지 하나를 클라이언트(미리보기·드라이런)와 Cloud Functions(커밋·진출 트리거)가 같이 import한다. 부수효과(Firebase I/O)는 엔진 밖에 둔다.
- **서버 권위(server-authoritative) 구조 변경**: 대진 생성, 진출, 일정 생성, 점수 정정, 기권 처리는 callable Function이 엔진을 호출해 multi-path update와 rev 검사로 원자적으로 처리한다. 클라이언트는 같은 엔진으로 미리보기만 한다.
- **경기 그래프**: 모든 슬롯은 출처(SlotSource)를 갖는다. 출처는 시드, 조 순위, 이전 경기의 승자·패자, 수동 지정 중 하나다.

### 2.2 패키지 위치
- 제안: `packages/engine/`(순수 TS, 런타임 의존성 없음, vitest)를 만들고 다음 두 경로로 참조한다.
  - Vite alias `@engine`
  - functions 빌드 시 번들: esbuild로 함께 번들하거나, tsconfig paths에 predeploy 복사를 더한다. predeploy 빌드는 커밋 77fd1a2에서 이미 존재한다.
- 이 방식은 **결정 D1**에서 확정한다.

### 2.3 핵심 타입 (요약)

```ts
// tournaments/{tid}/definition
interface FormatDefinition {
  version: number;                       // 스키마 버전 (마이그레이션 게이트)
  participantKind: 'player' | 'team';    // randomTeamLeague도 draw 후에는 'team'
  ruleSets: Record<string, RuleSet>;     // ScoringRules + 예상 소요시간 + 타이머
  defaultRuleSetId: string;
  tiebreakProfile: TiebreakProfile;      // 2.6
  stages: Record<string, StageDef>;
  placement: PlacementPolicy;            // 최종 순위 산출 규칙 (2.7)
  draw?: DrawPolicy;                     // 시드·서펜타인·국가/클럽 분리, 시드 난수 기록
}

interface StageDef {
  id: string; order: number; name: string;
  kind: 'round_robin' | 'single_elim' | 'double_elim' | 'swiss'
      | 'placement_bracket' | 'classification_rr' | 'manual';
  pools: Record<string, { name: string; size?: number }>;   // 조 개수 제한 없음 (현재 'ABCDEFGH' 8개 상한 제거)
  entry: EntrySource[];                 // 누가 들어오는가
  generator: GeneratorParams;           // 아래
  ruleSetId?: string;
  roundRuleOverrides?: Record<number, string>;  // 예: 준결승부터 5세트
  dependsOn: string[];                  // 스테이지 선행조건 (스케줄 H6)
  advancement: AdvanceRule[];           // 다음 스테이지로 누가 가는가
  ranking: { tiebreakProfileId?: string };
}

type EntrySource =
  | { kind: 'seedList' }                                        // 등록 선수/팀 (시드 순)
  | { kind: 'poolRank'; fromStage: string; pool: string | '*'; rank: number | [number, number] }
  | { kind: 'bestOfRank'; fromStage: string; rank: number; count: number }  // 와일드카드 (조간 비교)
  | { kind: 'matchOutcome'; matchKey: string; outcome: 'winner' | 'loser' }
  | { kind: 'manual' };

interface GeneratorParams {
  legs?: 1 | 2;                         // 단일/더블 라운드로빈
  rrOrder?: 'circle' | 'ibsa_table';    // IBSA 부록 경기순서 (D3 확인 후)
  seeding?: 'standard' | 'custom';      // 표준 시드 배치 1,16,8,9,4,13,...
  avoidSamePoolUntilRound?: number;
  byePolicy?: 'top_seeds';
  thirdPlace?: boolean;
  grandFinalReset?: boolean;            // double_elim
  swissRounds?: number; swissPairing?: 'dutch';
  placeRange?: [number, number];        // placement_bracket: 예 [5,8]
  teamTie?: TeamTieFormat;              // 2.5
}
```

**경기 문서(목표)**: `matches/{tid}/{mid}`

```ts
interface MatchV2 {
  stageId: string; poolId?: string;
  roundIndex: number;                    // 실제 라운드 (리그 라운드/대진 라운드). 실행 카운터 금지
  bracket?: 'W' | 'L' | 'GF' | 'P';      // winners/losers/grand final/placement
  slotIndex: number; matchKey: string;   // 결정적 키 예: "S2-W-R2-M1" → 멱등 생성
  side1: Side; side2: Side;              // { source: SlotSource, entrantId: string|null, displayName }
  winnerTo?: { matchKey: string; side: 1 | 2 };
  loserTo?:  { matchKey: string; side: 1 | 2 };
  ruleSetId: string;                     // 규칙 해석에 추측 금지
  outcome?: 'played' | 'walkover' | 'retired' | 'disqualified' | 'bye';
  outcomeReason?: string; decidedAt?: number;
  status: 'pending' | 'ready' | 'in_progress' | 'completed' | 'cancelled';
  rev: number;                           // CAS
  // 일정은 2.8 참고
}
```

- `bye`/`isBye`를 하나로 통일한다. 전환기 동안 엔진 어댑터가 둘 다 읽는다.
- `sourceMatch1/2` + `sourceType`(서버)과 `sourceMatch1Id`(클라이언트, types/index.ts:432)의 분열은 `winnerTo`/`loserTo` 정방향 링크와 역방향 `side.source`로 해소한다.
- **점수 이벤트 로그**: `matchEvents/{tid}/{mid}/{pushId}`에 append-only로 쌓는다. 배열 병합을 하지 않고 서버 타임스탬프를 쓴다. 이렇게 하면 "더 긴 배열이 이긴다" 규칙 때문에 이벤트가 유실되는 문제(useFirebase.ts:585-594)와 scoreHistory 정렬 혼재 문제(StatusTab.tsx:308 vs useIndividualScoring.ts:358)가 사라진다. 기존 scoreHistory는 읽기 전용 레거시로 남긴다.

### 2.6 순위·동률 규칙 (단일 모듈)
- `standings()` 하나만 남긴다. 다음 구현은 모두 삭제하거나 `standings()`로 대체한다.
  - ranking.ts의 3개 함수
  - rankings-compute.ts
  - generate-finals.ts:48-65, 84
  - FinalsSection.tsx:15-51
  - run-full-simulation.ts:362-406
  - rankings.ts:215-240
  - simulation.ts:376
- `TiebreakProfile` 기본값(IBSA 안, **D2에서 확정 필요**):
  1. 승수(경기 승점)
  2. 2인 동률이면 상대 전적
  3. 3인 이상 동률이면 동률자끼리의 미니 테이블(승 → 세트 득실 → 점수 득실). 동률이 일부만 풀리면 남은 집단에 처음부터 다시 적용(reapply)하는 방식과 전체 기록으로 넘어가는(fallback) 방식 중 하나를 옵션으로 둔다.
  4. 전체 세트 득실 → 전체 점수 득실 → 득점
  5. 기록이 남는 추첨(시드 난수와 수행자 감사로그)
- 이름순(localeCompare)으로 동률을 깨는 처리는 금지한다.
- **비교자를 쓰지 않고 그룹 분할 알고리즘으로 구현**해서 비이행성을 원천 제거한다.
- 세트 승자는 반드시 해당 경기의 ruleSet으로 판정한다. 현재는 기본 11점(ranking.ts:56), 서버는 p1>p2(rankings-compute.ts:98)로 서로 다르다.
- `outcome='bye'`는 모든 통계에서 제외한다.
- 기권·실격 선수의 리그 결과(유지 또는 무효)는 정책 필드로 둔다(**D4**).
- 출력: `{rank, tied: boolean, decidedBy: 'h2h'|'mini_table_sets'|...}`. 스크린리더에 "결정 기준: 상대 전적"처럼 읽어 줄 수 있게 한다.

### 2.7 최종 순위 (구조 기반)
- `finalPlacements()`는 다음 순서로 순위를 정한다: 결승 → 3/4위전 → placement_bracket 결과 → classification 티어 → 그 밖에는 탈락 스테이지와 라운드, 그리고 그 스테이지의 standings.
- 승수 합산 방식은 폐기한다(B4).
- 정해지지 않은 순위는 공동 순위로 표시한다. 예: "공동 5위" 또는 "5-8위". 정책으로 선택한다.

### 2.8 일정 저장 단일화
- 경기 문서의 `schedule: { date, start, end, courtId, refereeIds[], locked, source: 'auto'|'manual' }`를 단일 출처로 삼는다.
- `/schedule/{tid}` 그리드는 matches에서 파생한다. 전환기에는 서버가 matchId를 키로 원자적으로 재작성한다. 중복 슬롯 문제(useFirebase.ts:756-775)는 구조적으로 불가능해진다.
- `tournaments/{tid}/resources = { courtIds[], refereeIds[], sessions: [{date, start, end, breaks[]}], timeZone }`
  - 코트·심판을 대회 단위로 지정한다. 현재는 전역 /courts를 쓴다(schedule.ts:206; TournamentDetail.tsx:54-55).
- Referee와 Player에 `country`/`club` 필드를 추가한다(neutrality용; types/index.ts:242-249에 없음).

### 2.9 진출 트리거 (B1 해결)
- `onValueWritten(matches/{tid}/{mid})`: status가 completed로 바뀌거나 winnerId·outcome이 바뀌면 다음을 수행한다.
  1. 엔진의 `resolveSlots`로 하위 경기 슬롯 패치를 계산한다.
  2. 하위 경기가 `in_progress` 또는 `completed`이면 덮어쓰지 않는다. 대신 `conflicts/{tid}`에 기록하고 관리자에게 알린다.
  3. BYE와 부전승은 연쇄적으로 자동 진출시킨다.
  4. 정정으로 승자가 바뀌면 하위 슬롯을 재계산하고, 필요하면 비운다.
  5. 스테이지의 모든 경기가 끝나면 `resolveEntrants`로 다음 스테이지 슬롯을 채운다. 대진을 확정할지는 정책(auto 또는 관리자 확인)으로 정한다(**D5**).
- 같은 입력이면 같은 결과가 나와야 한다(멱등). rev 기반 트랜잭션이나 `tournaments/{tid}/rev` CAS로 동시 실행을 막는다.
- 관리자에게 보이는 자동 채움 결과는 aria-live로 알린다. 예: "준결승 1: QF1 승자 김OO 확정".

### 2.10 레거시 마이그레이션 계획
1. **읽기 어댑터(무중단)**: `legacyToDefinition(tournament, matches)`가 레거시 필드에서 definition을 유도한다.
   - 입력: format, formatType, stages, qualifyingConfig, finalsConfig, rankingMatchConfig
   - stageId 접미사 매핑: `_3rd`, `_class_N`, `5to8`, `knockout`, `group`, `third_place`
   - groupId `full_league`는 단일 pool로 바꾼다.
   - `sourceMatch1/2`는 역전해 `winnerTo`/`loserTo`로 만든다.
   - `bye`는 `isBye`(outcome='bye')로 바꾼다.
   - roundIndex는 bracketRound 라벨에서 재구성한다.
   - 이 어댑터로 엔진 전체가 레거시 대회에서도 돌아간다.
2. **일회성 마이그레이션 Function**: `definition.version`이 없는 대회에 대해 실행한다.
   - 먼저 backup.ts(:48, 77, 117)로 백업한다.
   - 어댑터 결과를 기록한다.
   - schedule/{tid}를 matchId 기준으로 중복 제거한다. 경기 필드와 일치하는 것을 남긴다.
   - **completed 경기는 내용을 변경하지 않고 메타 필드만 추가한다.**
3. **검증**: 에뮬레이터에서 프로덕션 사본으로 돌린다. 마이그레이션 전후의 standings와 finalPlacements diff 리포트를 만든다. 단, B4가 수정되면서 순위가 달라지는 것은 기대된 차이로 분류한다.
4. **완료된 과거 대회**: 어댑터로 읽기만 한다(재작성하지 않음). 이 방식을 기본으로 하되 **D9에서 확인**한다.

## 3. 스케줄링 엔진 설계

### 3.1 입력 모델
- **Match 작업**: `{matchKey, stageId, roundIndex, participants: entrantId[] | (TBD → 잠재 참가자 집합), duration, changeover, predecessors: matchKey[], pinned?}`
  - `duration`은 `ruleSet.expectedMinutes`에서 온다. 기본값 근거는 WC2025 실측이다: 3세트 경기 30분, 5세트 경기 45분, 단체 31점 경기 60분. 스테이지나 경기 단위로 덮어쓸 수 있고, 이후 완료 경기의 `actualStartTime`~`completedAt`으로 학습한다.
- **Resources**
  - courts: 날짜·시간 가용창 per court
  - referees: 가용창, country/club
  - sessions per date: start, end, breaks[]
  - timeZone(기본 Asia/Seoul)
- **Policy**
  - minRest: 이전 경기 **종료**부터 다음 경기 시작까지. 스테이지별로 지정한다.
  - maxMatchesPerDay: 선수별
  - unavailable windows: 선수별
  - stageGap
  - refereeMinGap, refereeMaxConsecutive, neutrality
  - categoryTableBlocks: 여러 종목이 테이블을 공유할 때

### 3.2 제약
**Hard 제약**
- H1: 같은 코트·같은 시각에는 한 경기만 배정한다.
- H2: 참가자 중복을 금지한다. 비교는 시간 **구간 겹침**으로 하며, 단체·랜덤팀은 팀원 단위로 확장한다.
- H3: 종료부터 시작까지 최소 휴식을 지킨다.
- H4: `[start, start+duration]`이 세션 안에 완전히 들어가고 모든 break 바깥에 있어야 한다.
  - 현재는 시작 시각만 검사한다(schedule-allocation.ts:151, 167; schedule-time.ts:55-60).
- H5: scheduleDates 안에서만 배정한다. 넘치면 넘기지 말고 실패로 보고한다(schedule-allocation.ts:94의 +1일 fallback 제거).
- H6: 선행관계. 경기는 `max(선행 경기 종료 + rest)` 이후에 시작한다. 스테이지는 dependsOn이 끝난 뒤에 시작한다. TBD 경기는 잠재 참가자의 휴식을 보수적으로 예약한다(CourtHive 방식).
- H7: 심판 1인 1경기, 최소 간격, neutrality. neutrality는 소프트 제약으로 둘 수도 있다.
- H8: 코트 가용창과 대회별 코트 집합을 지킨다.
- H9: pinned, in_progress, completed 경기는 고정된 점유로 취급한다.
  - 현재 '미배정만' 모드는 기존 배정을 무시한다(ScheduleTab.tsx:251-263; schedule-allocation.ts:112-119).

**Soft 제약 (사전식 목적함수)**
1. 사용 일수와 makespan을 최소화한다.
2. 최소 휴식을 최대화하고 연속 경기를 피한다(공정성).
3. 조별 진행을 균형 있게 한다. 한 라운드가 모든 조에서 끝난 뒤 다음 라운드를 시작한다.
4. 선수와 심판의 코트를 연속으로 유지한다.
5. 유휴 갭을 최소화한다.
6. 재스케줄 시 기존 계획에서 최소한만 바꾼다(안정성).

### 3.3 알고리즘
1. **사전 타당성 검사**
   - 필요한 코트-분(Σduration+changeover)과 가용 코트-분을 날짜별로 비교한다.
   - 선행관계 그래프의 임계경로 길이를 계산한다.
   - 부족하면 "N시간 또는 테이블 M개 추가 필요"를 출력하고 생성을 중단한다.
2. **시간 인덱스 리스트 스케줄러**: 5분 해상도 타임라인에서 우선순위 순으로 배정한다.
   - 우선순위: 위상 순서(stage.order, roundIndex) → 임계경로 잔여 길이 → 가능한 슬롯 수가 적은 것.
   - 코트 포인터를 단조 증가시키지 않고 **갭 back-fill**을 허용한다.
3. **로컬 서치 수리**: move/swap 연산과 시뮬레이티드 어닐링 또는 tabu로 soft 목적을 개선한다.
   - 시드 고정으로 결정적인 결과를 낸다.
   - 300경기 이하, 테이블 2~8개 규모에서 1초 미만으로 클라이언트와 Functions 모두에서 실행 가능하다(scheduling 감사 추정).
4. CP-SAT는 심판·neutrality 제약이 빡빡할 때만 별도 Cloud Run에서 쓴다. 현 단계 범위 밖이다(**D7**).

  explanations: Record<matchKey, string[]>; // "10:30 배정: QF2 종료(10:15)+휴식15분", "코트3: 코트1·2 점유"
  metrics: { makespan, daysUsed, minRest, avgRest, idleMinutes, perCourtUtil };

### 3.5 지연·재스케줄
- **예상 시작 시각(projected start)**: 실제 진행(actualStartTime, 코트별 평균 소요)으로 계산한다. "코트 2 15분 지연" 같은 메시지를 관리자·심판·관전 화면에 aria-live(polite)로 표시한다.
- **"지금부터 수리"(repair from now)**: completed, in_progress, locked 경기는 고정하고, 시작하지 않은 경기만 다시 계산한다. 이때 안정성 목적을 최우선으로 둔다. 결과는 diff 미리보기로 보여 주고 확인을 받은 뒤 커밋한다.
- **기존 일괄 이동과 코트 이동 교체**
  - 대상: pending 경기만. "경기 X 이후"나 "시각 T 이후"로 범위를 좁힐 수 있게 한다.
  - 커밋 전에 검증기를 실행하고, matches와 schedule을 하나의 multi-path update로 처리한다. 현재는 순차 await이라 중간에 실패하면 일정이 절반만 바뀐다(ScheduleTab.tsx:616-627).
  - 실행 취소 지원: 직전 상태를 감사로그에 저장한다.

### 3.6 수동 오버라이드
- 키보드로 쓸 수 있는 "이동…" 다이얼로그(코트·날짜(연도 포함)·시각 선택)를 기본으로 한다. 드래그는 시각 사용자를 위한 부가 기능이다.
- 저장 전에 검증기를 실행해 위반 목록을 보여 준다: 구간 겹침(코트·선수·심판), 휴식 부족, 세션 밖, 선행관계 위반.
  - 비교는 문자열 동일 비교가 아니라 구간 비교로 한다(ScheduleTab.tsx:94 개선).
  - 식별은 이름이 아니라 ID로만 한다(ScheduleTab.tsx:87의 '미정' 오탐 제거).
- 위반은 **경고**로 보여 주고, "그래도 저장(사유 입력)"을 허용한다. 저장한 경기는 `locked=true`가 되고 감사로그에 남는다.
- 검증기는 생성, 수동 편집, 이동, 수리 이후 항상 실행한다. 결과는 목록 형태 UI(role=alert 요약과 "해당 경기로 이동" 링크)로 보여 준다.

### 3.7 시간 처리
- `tournament.timeZone`을 추가하고 날짜 연산은 Y-M-D 정수 연산으로 한다.
- 다음 곳의 `toISOString()` 기반 '오늘' 계산을 제거한다: ScheduleTab.tsx:63, 459; TournamentCreate.tsx:114; schedule.ts:169.
- preMatchNotify의 KST 하드코딩(functions/src/index.ts:408-412)을 대회 timeZone으로 바꾼다.

## 5. 관리자 UX

### 5.1 흐름
1. **템플릿 갤러리**(개인전·단체전 모두): 각 카드는 스크린리더가 끝까지 읽는 평문 설명을 갖는다. 예: "IBSA 개인: 4인 조별리그, 조 2위까지 16강, 3/4위전, 9-32위 순위결정". 사용자 정의 템플릿을 저장할 수 있다.
   - 현재 프리셋은 2종(presets.ts:55-75)이고 개인전에서는 숨겨져 있다(Step1BasicInfo.tsx:313).
2. **스테이지 빌더**: 순서가 있는 목록 UI(카드 그래프가 아니라 목록). 각 스테이지에 다음을 지정한다.
   - 종류
   - 조 구성
   - 진입 규칙: "앞 스테이지 각 조 1~2위", "3위 중 상위 2명(와일드카드)"
   - 규칙 세트와 라운드별 override
   - 고급 옵션(접힘 상태, aria-expanded)
   - 스테이지 위·아래 이동은 각 버튼의 이름에 대상을 포함한다. 예: "스테이지 '본선' 위로".
   - 현재의 4가지 모드는 빌더를 채우는 프리셋으로 재정의한다.
3. **각 개념은 하나의 컨트롤에만 둔다**(시작 라운드, 3위전, 순위 범위, 점수 규칙). 현재는 Step2와 Step3에 중복되어 있다(Step2Participants.tsx:574-588 vs WizardStep4Finals.tsx:338-369).
4. **실시간 요약**: "32명, 8조×4, 조 2위 16강, 경기 48+16, 테이블 4개로 약 6.5시간". polite live region에 디바운스해서 갱신한다. 수치는 `countMatches()`와 스케줄 타당성 검사가 내놓은 실제 계산값만 쓴다.
5. **드라이런 미리보기**: 가상 참가자 N명으로 엔진을 실행한다. 쓰기는 하지 않는다.
   - (a) 대진을 중첩 목록으로 보여 준다. 예: "16강 3경기: A조 1위 대 B조 2위, 승자는 8강 2경기로".
   - (b) 스테이지별 경기 수
   - (c) 일자별 첫·마지막 경기 시각과 넘침 경고
   - 검토한 뒤에만 커밋한다.
6. **검증**: `validateDefinition`의 차단 규칙과 경고를 구분한다.
   - 상단에 오류 요약(role=alert, 각 필드로 이동하는 링크)을 두고, 필드마다 aria-describedby를 연결한다.
   - 경고는 "그래도 계속"을 허용한다.
   - 현재는 이름만 검증한다(TournamentCreate.tsx:361-369).
7. **생성 버튼 하나**, 저장 중에는 disabled. WizardStep5Preview.tsx:458-464의 중복 제출 버그를 제거한다.
8. **왕복 저장 보장**: 미리보기가 보여 주는 값은 저장되는 definition에서 렌더링한다. 별도 state를 쓰지 않는다. 이렇게 하면 B15와 TournamentCreate.tsx:553의 하드코딩이 구조적으로 해결된다.

### 5.2 접근성 필수 수정 (감사 근거)
- 스텝 전환 시 포커스를 각 스텝의 h2로 보낸다(현재는 이름 없는 div: TournamentCreate.tsx:384-387, 572).

## 7. 결정이 필요한 사항 (소유자)

1. **D1 엔진 패키지 위치와 빌드 방식**: `packages/engine` 모노레포(권장)와 `src/shared/engine`을 functions가 경로로 참조하는 방식 중 선택. 배포 파이프라인(predeploy)에 영향을 준다.
2. **D2 IBSA 동률 판정 순서**: 2인은 상대 전적, 3인 이상은 미니 테이블(세트 → 점수)로 두고, 마지막 수단(추첨 또는 시드)을 정해야 한다. 미니 테이블은 재적용 방식인지 전체 기록 fallback 방식인지도 정해야 한다. 공개 가이드라인 PDF가 404 상태라서 **현행 IBSA Showdown Guidelines 원문(위원회 문의)이 필요하다.** 조 크기별 경기 순서 부록을 쓸지도 함께 정한다.
3. **D3 조 편성 정책**: 세계랭킹 기반 서펜타인 + 국가·클럽 분리를 기본으로 할지, 시드 수동 지정을 우선할지.
4. **D4 기권·실격 정책**: 리그 도중 기권 시 남은 경기를 부전승으로 처리할지, 기존 결과까지 무효화할지. 부전패(default loss, 점수 무효)와 기권(giving up, 점수 유지)의 IBSA 구분을 그대로 적용할지.
5. **D5 스테이지 진출 확정 방식**: 예선 종료 시 결승 대진을 자동으로 확정할지, 관리자가 미리보기 후 확인해야 확정할지(권장: 확인).
6. **D6 여러 종목의 테이블 공유**: 남자·여자·단체 종목을 한 대회 안의 여러 event로 모델링할지, 여러 대회가 테이블 자원을 공유하는 방식으로 할지. 스케줄러 범위와 데이터 모델을 결정짓는다.
7. **D7 심판 배정 수준**: neutrality(국가·클럽)와 주·부심 자동 배정을 hard 제약으로 둘지 soft 제약으로 둘지. hard로 하고 제약이 빡빡하면 외부 솔버(Cloud Run CP-SAT)가 필요할 수 있다.
8. **D8 IBSA 결과 제출 포맷**: 필요 여부와 필수 필드. 선수 라이선스 ID, 국가, 등급 B1/B2/B3를 Player에 추가해야 한다.
9. **D9 과거 대회 처리**: 완료된 대회는 어댑터로 읽기만 할지(권장), 마이그레이션으로 재작성할지. 최종 순위 계산 방식이 바뀌면 과거 대회의 표시 순위도 달라질 수 있다는 점을 감안해야 한다.
10. **D10 미구현 형식의 노출**: 더블 엘리미네이션과 스위스를 M9 완료 전까지 UI에서 숨길지(권장), "준비 중"으로 표시할지.
11. **D11 챗봇 경로**: 챗봇의 구조 변경 도구를 계속 유지할지(같은 callable로 통합하고 감사로그를 남김), 아니면 읽기와 보조 기능으로 축소할지.
12. **D12 순위결정전 기본 범위**: 기본값을 "전 순위 결정"으로 할지 "상위 N위까지만"으로 할지. 경기 수와 일정 길이에 직접 영향을 준다.

# 부록: 비판적 검토 (Critic)

## 회의적 검토 결과 (읽기 전용, file:line 직접 확인)

### 1. 현재 코드에 대한 주장 중 틀렸거나 부정확한 것
1. **B9: "1·2번 시드가 4강에서 만난다"는 일부만 맞고, 실제 문제는 더 심각하다.**
   - seedBracket은 성적으로 조 1위끼리 순위를 매기지 않는다. 배열을 "A1,B1,C1…, 2위 역순"으로 이어 붙일 뿐이다(bracket-seeding.ts:31-36). 즉 "1번 시드"는 그냥 A조 1위다.
   - 4조×2명이면 seeded=[A1,B1,C1,D1,D2,C2,B2,A2]가 되고, fold 짝(:43-49)이 A1-A2, B1-B2, C1-C2, D1-D2로 **모두 같은 조**다. 이를 greedy 스왑(:62-89)이 사후에 수습하는 구조다.
   - 다음 라운드는 인접 슬롯을 묶는다(generate-finals.ts:215-216). 그래서 16강 대진에서는 A1과 B1이 **8강**에서 만난다. "4강"은 8강 대진일 때에만 맞는 표현이다.
2. **B7 "필드를 지울 수 없다"는 과장이다.**
   - null을 넘기면 지워진다. 심판 코드도 이미 null을 쓴다(useIndividualScoring.ts:100-108).
   - 실제로 고장 난 곳은 undefined를 넘기는 호출부뿐이다: ScheduleTab.tsx:188, useIndividualScoring.ts:80(`value || undefined`).
3. **B14 "큐잉 실패를 성공으로 보고한다"는 관리자 경로에만 해당한다.**
   - useMatches.updateMatch는 큐에 넣은 뒤 true를 반환한다(useFirebase.ts:495-496).
   - 심판이 쓰는 useMatch.updateMatch는 false를 반환한다(useFirebase.ts:605-606).
4. **D8과 2.8 "Player에 B1/B2/B3와 club을 추가해야 한다"는 틀렸다.** Player에는 이미 `club`과 `class`가 있다(types/index.ts:235-236). 없는 것은 country와 라이선스 ID, 그리고 Referee의 country/club(types/index.ts:242-249)이다.
5. **라운드별 규칙 override와 수동 대진은 "신규"가 아니다.** `RoundScoringOverride`(types/index.ts:56)와 `FinalsStageConfig.roundScoringOverride`, `customBracketPairings`(:111-112)가 이미 있다. legacyToDefinition 어댑터의 매핑 목록에 빠져 있다.
6. **D1 "tsconfig paths + predeploy 복사"는 런타임에서 동작하지 않는다.**
   - predeploy는 tsc만 실행한다(firebase.json `predeploy`).
   - functions/tsconfig.json에는 rootDir가 없고 include가 ["src"]다. 상위 패키지를 import하면 tsc가 rootDir를 상위 폴더로 추론해서 출력이 `lib/functions/src/...`로 바뀐다. 그러면 `main: lib/index.js`(functions/package.json)가 깨진다.
   - 배포 때 functions/ 폴더만 업로드된다. 따라서 **번들링(esbuild)이나 functions/ 내부로 복사**하는 것이 사실상 유일한 선택지다.
7. **"클라이언트에서 서버 경로는 챗봇뿐이다"는 부정확하다.** 클라이언트는 이미 onRequest 함수를 fetch로 호출한다(useAuth.ts:13,27; useChatbot.ts:20). callable 방식을 쓰려면 firebase/functions SDK를 새로 도입해야 한다.
8. **5.2 "axe를 건다"는 "확장한다"로 고쳐야 한다.** 이미 있다: e2e/accessibility.spec.ts, @axe-core/playwright(package.json:29).
9. **확인된 주장**: B1(sourceMatch를 읽는 곳은 simulate.ts:105,517뿐이고 onMatchChange는 onValueUpdated로 푸시만 보냄, index.ts:227), B6(schedule-allocation.ts:194), H5 fallback(:94), B8(useFirebase.ts:504-527, 640-652, 756-775와 ScheduleTab.tsx:398의 이중 보존), B12(StatusTab.tsx:262-280), B4(RankingTab.tsx:35-41), 심판의 전 대회 쓰기(database.rules.json:35).
10. **설계에 빠진 사실 두 가지**
    - DB 규칙이 match status를 pending/in_progress/completed로만 허용한다(rules:38). MatchV2의 `ready`/`cancelled`는 전부 거부된다.
    - type은 individual/team만 허용한다(rules:40). 그런데 generate-finals는 `tour2.type`을 그대로 기록한다(:139). 그래서 randomTeamLeague 결승 경기를 심판이 transaction으로 통째로 쓰면 validate에서 거부될 가능성이 높다. **[불확실: 에뮬레이터로 확인 필요]**

### 3. 로드맵 위험

  - 이를 다루는 마일스톤이 없다.
  - 기존 필드(player1Id 등)를 유지하고 필드를 추가만 하는 expand-contract 방식이 필요하다.
- **M11(마이그레이션)이 맨 끝에 있다.** 그 전까지 신규 코드가 미검증 레거시 데이터 위에서 돈다. 프로덕션 스냅샷 fixture는 M1 시점에 확보해야 한다.

> "이 앱으로 **모든 대회 운영과 중계 확인**이 가능해야 한다. **어떤 조건의 대회 방식도** 진행 가능해야 한다."

## A. "어떤 방식이든" 보장 조건 (모든 마일스톤의 수용 기준에 적용)
1. **조합 가능성**: 대회 = 단계(stage)의 그래프. 각 단계는 생성기(풀리그 1·2회전, 조별, 단일·더블 엘리미네이션, 스위스, 순위결정전, 단체 tie, 수동) + 진출 규칙 + 순위 규칙의 조합. 단계 수·조 수·인원 제한 없음.
2. **탈출구(escape hatch)**: 엔진이 지원하지 않는 특수 방식은 `manual` 단계(관리자가 대진을 직접 입력, 엔진은 검증·일정·순위·중계만 담당)로 반드시 운영 가능해야 한다. "지원 안 됨 → 대회 불가"인 경우가 없어야 한다.
3. **규칙 유연성**: 세트 수·점수(11/21/31점)·2점차·타임아웃·워밍업을 대회/단계/라운드/경기 단위로 덮어쓸 수 있다.
4. **운영 중 변경**: 진행 중에도 단계 추가, 대진 수정, 기권·실격, 늦은 참가, 경기 재개·정정이 가능하고 하위 결과가 일관되게 재계산된다.
5. **검증 방법**: 형식 매트릭스 테스트 — 대표 대회 템플릿(세계선수권형 조별+전순위, 소규모 풀리그, 단판 토너먼트, 더블 엘리미, 스위스, 단체 리그+결승, 랜덤팀, 수동 혼합)마다 생성→시뮬레이션→진출→일정→최종순위→중계 화면까지 자동 E2E(에뮬레이터)로 통과.

# 부록 3: M0c 구현 메모 (대회 규칙 단일 설정원)

> 소유자 요구: "부전승은 11:0으로 승리하는 것이고, 대진 방식 등 설정을 커스텀으로 했을 때 모든 대회 운영이 매끄럽게 이어지는 구조"

## 규칙 단일 설정원
- 위치: `src/shared/rules/` (순수 TS). functions는 상위 폴더를 import할 수 없으므로(부록 1의 D1 지적) `node scripts/sync-shared-rules.mjs`로 `functions/src/shared/rules/`에 사본을 두고, `functions/src/shared/rules.sync.test.ts`가 원본과 다르면 실패한다. M1에서 esbuild 번들로 바꾸면 사본은 지운다.
- 저장: `tournaments/{tid}/rules`(대회), `stages[i].rules`(스테이지), `rules/tiebreakDecisions/{key}`(관리자 동률 결정). 부분 값만 저장하고 나머지는 우선순위로 채운다.
- 우선순위: 기본값 → 프리셋(`ibsa` 'IBSA 기본', `simple` '간단') → 레거시 대회 필드(gameConfig, teamMatchSettings, scoringRules, rankingMatchConfig, finalsConfig, tiebreakerRules) → `tournament.rules` → 레거시 `stage.scoringRules` → `stage.rules`. 경기 점수는 그 위에 `match.appliedScoringRules`. 하위 스테이지 ID(`{finals}_3rd`, `_class_N`)는 부모 스테이지 규칙을 쓴다.
- 순위는 저장하지 않고 계산한다. 규칙을 바꾸면 관리자·관전 화면 순위가 즉시 다시 계산된다.

## 부전승 = 11:0 (M0e 동작을 뒤집음)
- 기권/불참 부전승과 상대 없는 BYE 모두 "세트 목표 점수 : 0 × 이겨야 하는 세트 수"를 기록한다(3세트제 11:0 ×2, 5세트제 ×3, 팀 31:0). `walkover.setScore`로 점수를 바꿀 수 있다.
- 기본으로 순위표·선수 통계에 일반 승리처럼 들어간다. 끄는 설정: `countInStandings`, `countInPlayerStats`, `byeCountsAsWalkover`.
- BYE-vs-BYE는 경기 없음(승자 없음, 집계 안 함). 일정·경기 수 제한(countPlayableMatches)은 계속 BYE를 뺀다.
- 쓰기는 `isBye` + `walkover` + `walkoverReason`('bye' 또는 사유)만, `bye`는 읽기 호환만.

## 동률 (B11)
- 기준 순서(설정 가능): 승점 → 상대 전적(동률자끼리 미니 테이블) → 세트 득실 → 점수 득실 → 득점. 추가 기준: 승수, 세트/점수 득실률, 추첨.
- `headToHeadMode`: recursive(일부가 갈리면 남은 집단에 처음부터 다시 적용, 상대 전적도 작은 집단끼리 재계산) / single_pass.
- 미해결 동률은 이름순으로 정하지 않고 "미해결"로 돌려준다. 정책: `admin_decision`(기본, 관리자 화면에서 순서 확정 → 기록), `lot`(저장된 `lotSeed`로 재현 가능한 추첨, seed 없으면 미해결), `playoff`.
- **[소유자 확인 필요 — D2]** 기본 순서는 IBSA Showdown 현행 가이드라인 원문 확인 전 잠정안이다. 원문을 받으면 `DEFAULT_TIEBREAK_CRITERIA`만 바꾸면 된다.

## 시드 (B9·B13)
- 표준 시드 위치(1·2번 시드는 결승에서만), BYE는 상위 시드에게, 조 1위 → 조 2위 → 와일드카드 계층 순 시드, 같은 계층 안에서 같은 조가 가장 늦게 만나도록 결정적으로 자리 교환. 2개 조면 A1-B2, B1-A2.

## 최종 순위 (B4)
- 결승 → 3/4위전(`thirdPlace: match`, 없거나 `joint`면 공동 3위) → "X/Y위 결정전" → "N~M위 순위 결정전" 리그 → 남은 라운드 패자(`fifthToEighth`/`lowerPlaces`: 공동 또는 예선 성적순). 대진이 없으면 순위표 + 동률 규칙.

# 부록 4: 자가 확장 규칙 엔진 (소유자 요구, 2026-11-28)

**요구:** 요강을 넣으면, 기존 데이터나 설정 항목에 없는 규칙이라도 엔진이 스스로 만들어 적용해야 한다.

## 원칙
1. **규칙은 데이터가 아니라 프로그램이다.** 고정된 설정 항목 목록으로는 처음 보는 규칙을 담을 수 없다. 그래서 M1 엔진은 처음부터 **작은 기본 연산(프리미티브)과 이를 조합하는 안전한 규칙 언어(DSL)**로 설계한다. FormatDefinition, CompetitionRules, 동률 기준, 진출 조건, 대진 매핑, 일정 제약이 모두 이 언어로 표현된다.
   - 예: "4인조 3위 중 상위 2명" = `filter(rank==3, groupSize==4) → sort(tiebreak) → take(2)`
   - 예: "동률이면 나이 어린 선수" = 동률 기준 목록에 `compare(player.birthDate, desc)` 추가
2. **AI(요강 해석기)는 새 규칙을 이 언어로 작성한다.** 프리미티브로 표현되면 조합으로 만든다. 표현이 안 되면 새 프리미티브를 **샌드박스 안의 순수 함수**로 생성한다. 이 함수는 입력이 같으면 결과가 같아야 하고, 네트워크·DB·시간·난수에 접근할 수 없으며, 엔진이 넘겨준 데이터만 읽는다.
3. **검증 없이는 적용하지 않는다.**
   - (a) 쉬운 말 설명과 **구체적 예시 판정**을 보여 준다. 예: "A 2승1패, B 2승1패, 맞대결 A 승이면 A가 위"
   - (b) 타입·불변식 검사를 한다. 모든 경기에 선수 둘, 중복 없음, 순위가 빠짐없이 매겨짐, 진출 인원 일치, 시간표 충돌 없음.
   - (c) 가상 결과 수천 건으로 모의 실행하고, 무한 루프·미결정·모순을 검출한다.
   - (d) 관리자 승인을 받는다.
4. **판정은 항상 결정적으로 한다.** 경기 중 AI는 결과를 정하지 않는다. 승인된 규칙 프로그램만 실행하며, 대회에 버전으로 고정해 같은 기록은 언제나 같은 결과가 나오게 한다. 오프라인이나 대회장에서도 작동한다.
5. **"학습" = 규칙 라이브러리의 축적.**
   - 승인된 규칙과 새 프리미티브는 이름, 설명, 출처 요강, 테스트와 함께 라이브러리에 저장한다.
   - 다음 요강을 해석할 때 AI가 라이브러리에서 비슷한 규칙을 찾아 먼저 재사용한다. 모델 가중치를 학습시키는 것이 아니라, 검증된 규칙이 쌓여 엔진이 스스로 넓어지는 구조다.
   - 각 요강은 재현 픽스처(docs/06 §6)로 추가되어 회귀 테스트가 된다.
6. **최후의 탈출구는 수동 단계다.** AI가 규칙을 만들지 못하거나 검증에 실패하면, 그 부분만 수동 단계로 진행한다. 이때도 점수, 순위, 일정, 중계는 유지된다.

## 로드맵 반영
- **M1(엔진 골격):** 프리미티브와 DSL, 결정적 실행기, 불변식 검사기, 규칙 버전 고정을 먼저 만든다. 기존 CompetitionRules는 DSL로 컴파일되는 "기본 라이브러리"가 된다.
- **신규 M-AI1(요강 해석기):** HWP/PDF/텍스트 → DSL 초안, 모호점 질문, 예시 판정, 모의 실행, 승인 화면(접근성 포함)을 만든다.
- **신규 M-AI2(규칙 생성·라이브러리):** 새 프리미티브 생성(샌드박스), 라이브러리 저장·검색·재사용, 픽스처 자동 추가를 만든다.
- 보안: 생성 코드는 서버 샌드박스(격리 워커, 시간·메모리 제한)와 클라이언트 양쪽에서 같은 결과를 내야 한다. 관리자만 승인할 수 있다.
